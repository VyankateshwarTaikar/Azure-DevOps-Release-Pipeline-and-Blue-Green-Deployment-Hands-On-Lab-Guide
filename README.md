# Azure DevOps Release Pipeline and Blue-Green Deployment — Hands-On Lab Guide

This hands-on lab continues the **YouTube clone** project and demonstrates an Azure DevOps **multi-stage Release Pipeline**, **continuous deployment trigger**, **deployment gates**, **pre-deployment approval**, **Azure App Service deployment slots**, and **blue-green deployment**.

---

## Demo 1 ==> Create and Configure Azure DevOps Multi-Stage Release Pipeline

# MAIN DEMO: Create and Configure Azure DevOps Multi-Stage Release Pipeline

## 1. Open the Existing Azure DevOps Project

1. Open the existing **Azure DevOps project** created for the previous YouTube Clone project.
2. Navigate to:

   **Pipelines → Releases**

3. If no Release Pipeline exists, click **New pipeline**.

> **Additional Information:** The (Demo step stated) uses the same **YouTube clone** project from the previous video.

---

## 2. Start a New Release Pipeline

1. On the Release Pipeline creation screen, select a template.
2. Select:

   **Azure App Service deployment**

3. The Release Pipeline uses a GUI-based configuration rather than YAML.

> **Additional Information:** The (Demo step stated) notes that Classic Release Pipelines provide GUI-based features such as **quality Gates** and **approval**.

---

## 3. Rename the First Stage

1. Rename the default stage to:

   **Dev deployment**

2. Close the stage configuration.

The Release Pipeline now contains:

- **Artifacts**
- **Stages**

---

## 4. Add the Build Artifact

1. Click:

   **Add an artifact**

2. Set the source type to:

   **Azure Build**

3. Select the project:

   **YouTube clone**

4. From the build pipeline drop-down, select:

   **YouTube clone**

5. Keep the default version configuration.

6. Click:

   **Add**

> **Additional Information:** The artifact is the build artifact generated by the Azure DevOps build pipeline.

If a specific build version is required, the (Demo step stated) demonstrates selecting:

**Specific version**

instead of the default/latest version.

---

## 5. Configure the Continuous Deployment Trigger

1. Locate the artifact.
2. Click the **thunder icon** associated with the artifact.
3. This opens the **Continuous deployment trigger** configuration.
4. Enable the continuous deployment trigger.
5. Configure the branch from which the build should be available.
6. Use the **build pipeline default branch**.
7. Multiple branches can be configured if required.

> **Additional Information:** The purpose of the Continuous Deployment trigger is to automatically create a Release when a new build artifact becomes available.

---

## 6. Configure Pull Request Trigger

1. Review the **Pull request trigger** option.
2. This can create a Release when the selected artifact becomes available as part of a pull request workflow.
3. For this lab, keep the trigger focused on a **new build being created**.

---

## 7. Review the Schedule Trigger

1. A schedule can also be configured.
2. Enable the schedule if deployment needs to occur at a particular time/day.
3. For this lab, do not use the schedule.
4. Use the **Continuous deployment** trigger.

---

## 8. Configure Dev Deployment Pre-Deployment Conditions

1. Open the **Dev deployment** stage.
2. Open:

   **Pre-deployment conditions**

3. Configure the trigger as an automatic trigger after the preceding stage/release is available.
4. Configure the **Artifact filter** if required.
5. Select the required branch, such as the **main branch**.

> **Additional Information:** The (Demo step stated) also identifies schedule, pull request deployment, and pre-deployment approval as available options. Approval will be configured for the production deployment rather than the test/development deployment.

---

## 9. Configure the Dev Deployment Job

1. Open the Dev deployment stage.
2. Click:

   **Add job and task**

3. Select the **Azure subscription** from the drop-down.
4. Use the existing Azure service connection.
5. Set the application type to:

   **Web App on Linux**

6. Select the existing **App Service** created for the YouTube clone.
7. Leave:

   **Startup command**

   blank.

8. Configure the agent:

   **Azure Pipelines**

9. Select:

   **Ubuntu latest**

> **Additional Information:** The (Demo step stated) uses the same agent configuration as the build pipeline.

10. The Release Pipeline downloads the artifact generated by the previous build stage.

---

## 10. Configure Deployment to an App Service Slot

1. In the deployment task, verify:

   **Connection type:** `Azure Resource Manager`

2. Verify:

   **Web App on Linux**

3. Locate:

   **Deploy to slots or App Service environment**

4. Enable deployment to a slot.

5. Select the required:

   - Resource Group
   - App Service
   - Deployment Slot

6. At this point, the (Demo step stated) does not yet have a slot configured, so create one in Azure Portal.

---

# Demo 2 ==> Configure Query Work Item Deployment Gate and Production Approval

# MAIN DEMO: Configure Query Work Item Deployment Gate and Production Approval

## 1. Open Azure Boards

1. Open the **YouTube clone** project.
2. Navigate to:

   **Boards**

3. Create a new work item.
4. Select:

   **Task**

5. Give the task the name:

   **quality gate check**

6. Keep it in the **To Do** state.
7. Save the work item.
8. Change the state to:

   **Doing**

9. Save it.

---

## 2. Create a Shared Query

1. Navigate to:

   **Boards → Queries**

2. Create a new query.
3. Add the filter:

   **Priority**

4. Set:

   **Priority = 1**

5. Remove unnecessary/default filters.
6. Save the query.
7. Name the query:

   **P1 tasks**

8. Save it under:

   **Shared Queries**

> **Additional Information:** The query must be available as a shared query so that the Release Pipeline can access it.

---

## 3. Verify the Query

1. Open the newly created:

   **P1 tasks**

2. Check the results.
3. Initially, there are no matching P1 work items.

4. Return to the **quality gate check** task.
5. Change its priority from:

   **P2**

   to:

   **P1**

6. Save the work item.

7. Return to:

   **Boards → Queries → Shared Queries**

8. Open:

   **P1 tasks**

9. Verify that the task now appears in the results.

---

## 4. Create a Query Chart

1. Open the query results.
2. Go to the chart section.
3. Create a chart.
4. Select:

   **Group by work item type**

5. Save the chart.
6. Verify that the P1 task appears.

---

## 5. Add the Query Work Item Deployment Gate

1. Return to the Azure DevOps **Release Pipeline**.
2. Open the deployment gate configuration.
3. If the query is not immediately visible, close and reopen the configuration to refresh it.
4. Click **Add** under deployment gates.
5. Select:

   **Query Work Item**

6. Set the display name to:

   **query work item**

7. Select the previously created query:

   **P1 tasks**

8. Configure the **Upper threshold**.

9. Set:

   **Upper threshold = 2**

> **Additional Information:** The upper threshold represents the maximum number of matching work items from the query that the gate can take into account.

10. Open **Advanced**.
11. Keep:

   **Lower threshold = 0**

---

## 6. Configure Deployment Queue Settings

1. Configure:

   **Maximum number of parallel deployments**

2. Set:

   **1**

3. Configure subsequent releases according to the required deployment behavior.

Available options demonstrated in the (Demo step stated) include:

- **Deploy all in sequence**
- **Deploy latest and cancel the other**

---

## 7. Review Other Deployment Gate Options

The Release Pipeline can also use other gate mechanisms.

The (Demo step stated) identifies options such as:

- **Invoke REST API**
- **Invoke Azure Function**
- **Check Azure Policy Compliance**
- **Query Azure Monitor Alerts**

For this lab, continue using:

**Query Work Item**

---

## 8. Correct the Work Item Query Condition

The original query only checks:

**Priority = 1**

That means even a completed P1 work item can still match the query.

1. Open:

   **P1 tasks**

2. Select:

   **Editor**

3. Add another clause:

   **State**

4. Configure the state condition so that completed work items are excluded.

Use:

**State != Done**

> **Correction:** The (Demo step stated) first describes selecting **State → Done** and then selecting the operator meaning **not equal to done**. The technically relevant final condition is **State != Done**, because the gate should block deployment when an unresolved P1 work item exists.

5. Save the query.
6. Open the query results.
7. Verify that there are no results when the P1 task is already **Done**.

---

## 9. Configure Work Item Access Permissions

The Release Pipeline may require permission to access the work item query.

1. Open the work item query in a new tab.
2. Locate the query.
3. Click the **three dots** next to the query.
4. Select:

   **Security**

5. Locate the project build service identity.
6. Search for:

   **YouTube clone build service**

7. Select the build service identity associated with the organization/project.
8. Ensure that:

   **Read permission = Allow**

> **Additional Information:** The (Demo step stated) identifies this permission as important for preventing **quality Gates** from failing because the pipeline cannot access the work item/query.

---

## 10. Configure Production Stage

1. Return to the Release Pipeline.
2. Clone the existing **Dev deployment** stage.
3. Rename the cloned stage to:

   **prod deployment**

4. Open:

   **Pre-deployment conditions**

5. Configure the production stage to run after the test/development deployment.

> **Additional Information:** The intended sequence is:

```text
Build
   ↓
Dev deployment
   ↓
Prod deployment
```

---

## 11. Configure Production Pre-Deployment Approval

1. In **prod deployment**, open:

   **Pre-deployment approvals**

2. Add the required approver.
3. For the demonstration, add the current user as the approver.
4. Review the approval timeout.

The (Demo step stated) states:

**30 days**

5. Review the option preventing the user who requested the deployment from approving it.
6. For this demonstration, leave that option at its default configuration.

> **Additional Information:** Production deployment requires manual approval before the deployment can proceed.

---

## 12. Configure Production Deployment Job

1. Open the production stage.
2. Open the deployment job.
3. Keep the same deployment configuration as the Dev deployment.
4. Change the deployment target from the staging slot to the production slot.

5. The production slot is the default live App Service slot.

> **Correction:** The production slot does not need to be selected as a named deployment slot in the same way as `staging`. In Azure App Service, the default production slot is represented by the main App Service. Disable the slot-specific deployment selection so the task deploys to the production slot.

6. Save the Release Pipeline.

---

## 13. Remove Deployment from the Build Pipeline

The build pipeline should create and publish the artifact, while the Release Pipeline handles deployment.

1. Open the existing **build pipeline** in a new tab.
2. Click:

   **Edit**

3. Locate the deployment stage previously configured in the build pipeline.
4. Remove the deployment stage.
5. The deployment stage contains two tasks:

   - **Download artifacts**
   - **Deployment**

6. Delete these deployment tasks.

> **Additional Information:** Deployment is now handled by the Release Pipeline.

7. Save the build pipeline.

The intended build process is now:

```text
Azure Repos
    ↓
Build Pipeline
    ↓
npm install
    ↓
npm build
    ↓
Publish Artifact
    ↓
Release Pipeline
```

---

## 14. Trigger and Validate the Build Pipeline

1. Save the build pipeline.
2. Because Continuous Deployment is configured, the build should trigger the Release Pipeline after producing an artifact.
3. Navigate to:

   **Pipelines**

4. Verify that the build has been queued.
5. Open the running build.
6. Wait for the build to complete.
7. Verify that:
   - The build completes without errors.
   - An artifact is produced.

## 15. Verify Release Pipeline Trigger

1. Navigate to:

   **Releases**

2. Verify that a new Release has been created.
3. Open the Release.
4. Verify that the artifact was successfully downloaded.
5. Open the logs.
6. Verify that the deployment gate is being evaluated.

---

## 16. Verify the Quality Gate Failure Scenario

Initially, the query contains a blocking P1 work item.

1. Open the Release logs.
2. Observe the query work item gate.
3. The gate should fail because a matching blocking work item exists.

> **Additional Information:** The (Demo step stated) explains that if a work item has **Priority = P1** and is not in the **Done** state, the deployment should not proceed.

4. The gate evaluation interval is shown as approximately **5 minutes by default** in the (Demo step stated).
5. The next evaluation occurs after the configured evaluation interval.

---

## 17. Resolve the Blocking Work Item

1. Open the **quality gate check** work item.
2. Change its state from:

   **Doing**

   to:

   **Done**

3. Save the work item.

4. Open the:

   **P1 tasks**

   query.

5. Verify that the completed work item no longer appears because the query now excludes:

   **State = Done**

---

## 18. Re-run the Build and Release Process

1. Return to the build pipeline.
2. Make/save the required pipeline changes.
3. The build should trigger.
4. Open the running build.
5. Wait for the build to complete.
6. Verify that an artifact is generated.

7. Open the Release Pipeline.
8. Verify that a new Release is created.
9. Verify that the **quality gate check** succeeds.

> **Additional Information:** The (Demo step stated) states that the gate is evaluated consecutively according to its configuration. Once the required evaluations succeed, deployment proceeds.

---

## 19. Verify Deployment to Staging

1. Open the Release logs.
2. Verify that deployment proceeds to the **staging environment**.
3. Monitor the deployment logs.
4. Wait until the deployment completes.

5. Open the staging URL.

6. Verify that the URL contains:

   **staging**

> **Additional Information:** The staging slot has its own URL, separate from the production application URL.

---

## 20. Approve Production Deployment

1. Return to the Release Pipeline.
2. Open the **prod deployment** stage.
3. The stage should wait for **pre-deployment approval**.
4. Approve the deployment directly from Azure DevOps.

The (Demo step stated) also demonstrates approval through email:

1. Open the approval email.
2. The email identifies:
   - Pipeline
   - Release
   - Stage
3. Click:

   **View approval**

4. On the approval page, click:

   **Approve**

5. Optionally add a comment such as:

   **looks good to me**

6. Click **Approve**.

## 21. Verify Production Deployment

2. Verify that:
   - Pre-deployment approval completed.
   - Deployment Gates completed.
   - Agent deployment completed.
3. Open the production URL.
4. Refresh the application.
5. Verify that the new application version is now running in production.

## 9. Understand the Staging and Production Slots

The completed architecture contains two application environments:

```text
                 Azure App Service
                       |
          +------------+------------+
          |                         |
      Production                  Staging
       Slot                         Slot
          |                         |
     Live version              New version
```

The staging environment provides an isolated environment where the new application version can be deployed and validated before production.

## 14. Understand the Blue-Green Deployment Model

The (Demo step stated) represents the environments conceptually as:

```text
Blue  → Production
Green → Staging
```

For example:

```text
Blue  → Version 1.0
Green → Version 2.0
```

The new version is deployed to the green environment while the blue production environment continues serving users.

> **Additional Information:** The purpose is to avoid application downtime during deployment by keeping the existing application available while the new version is prepared.

---
